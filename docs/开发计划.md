# Fit-Extended 完整开发计划

## 0. 结论与执行边界

**在工作区已有 FE 1.6.0 上增量改造，不重写工程。六类文件处理规则共用一套“检查 → 计划 → 审阅与决策 → 执行 → 记录结果”流程；人工审阅是第七项能力，不另建一套同步引擎。轻量化是硬约束。**

本计划以[已确认需求][requirements]为准。当前任务只制定计划：没有修改插件源码、安装插件、运行同步、构建或测试，没有访问真实插件配置和凭据。文中的新增接口、测试与验收结果均为后续工作，不是已完成事项。

- 开发基线：[工作区现有 FE 工程][source-root]。目录名称包含 `source-1.5.0`，但当前[工程配置][package]及[插件清单][manifest]均为 `fit-extended` 1.6.0，不能误用上游 1.5.0 当作重新开工的基线。
- 已核验本地提交：`d145df26806ec8358ec53f5aab05103c753b3211`；只读检查时 Git 工作树无未提交变化。这是计划编制时的快照，实际开工时只确认是否出现并发改动，不重新克隆或核对整个 GitHub fork。
- 现有产物尺寸：主 bundle 310,041 字节，样式 18,001 字节，清单 419 字节。它们仅是磁盘文件尺寸，不代表本轮已复现构建或测得启动性能。
- 保留已有插件身份、认证、仓库和分支配置；不做原 FIT 配置导入，不重置已有 FE 数据。
- 不新增完整 Git 客户端、历史恢复、备份库、日志中心、文件管理器或定时同步；不增加目录或单文件同步入口。
- 仅支持 GitHub。Obsidian 桌面和移动端兼容必须保留。

## 1. 固定需求与开发映射

| 已定能力 | 实现要点 | 关键验收 |
|---|---|---|
| 仅补充缺失文件 | 比较当前两端是否存在；目标已存在绝不覆盖，不依赖来源是否相对历史发生变化 | 目标主动删除后可补回；来源新增但目标已存在时不得覆盖 |
| 单向更新 | 根据逐路径共同状态判断双方变化；来源单改才更新，目标单改保持，双方不同则交用户决策 | 目标删除、来源未改则不补回；来源也改则显示冲突；无基线同名不同不能自动覆盖 |
| 单向覆盖 | 来源存在的同名差异以来源为准，保留目标独有文件 | 来源未变化但目标变了，仍应正确生成覆盖计划 |
| 单向镜像 | 来源内容和路径集合为准；删除整个知识库实际同步范围内的目标独有文件 | 包括可同步的未跟踪文件；忽略对象、元数据和范围外文件不删除 |
| 双向合并、不传播删除 | 新增与修改双向交换；单端缺失则补回；改名按路径处理，不移除旧路径 | 文件复活、新旧名并存；双方都没有不从历史恢复；双方不同修改交用户决策 |
| 双向同步、传播删除 | 基于共同状态区分新增与删除，识别修改—删除冲突 | 首次未知不误判删除；双方最终内容相同不产生假冲突 |
| 人工审阅后同步 | 共用预览、逐项勾选、全选、取消、依赖联动和冲突决策 | 确认前不应用文件变化；未选项不视为已同步 |

前四类规则均复用已有上传、拉取方向。所有操作入口只针对整个知识库；预览时逐项勾选是既有审阅要求，不增加独立单文件或目录入口。

默认操作固定为“双向同步、传播删除 → 先审阅再执行”。冲突显示双方差异并交用户决策，不新增暂停按钮、锁定状态或恢复流程。尚未作出决策的冲突不能被全选操作自动选定一方；用户的选择、取消及确认仍在同一个审阅流程内完成。

如果镜像计划只选择部分项目，本次只执行选中的操作，不宣称目标已经完整镜像；只有全量选定且成功时才检查全量一致。

## 2. 现有代码：复用什么、修正什么

本节为源码静态核验结果，不沿用旧交付说明中的测试数量或“全部通过”结论。

| 现有部分 | 可复用 | 必须修正 |
|---|---|---|
| [单向操作核心][directional] | 计划对象、准备与执行分离、执行前本地/远端校验、运行互斥 | 当前主要按来源历史增量生成动作，不能完整表达补缺、覆盖、镜像；整体保存状态不适合逐项选择 |
| [双向同步][fit-sync] | 本地和远端适配器、读写与结果表达的部分实现 | 不能继续直接同步或先写冲突副本再继续，必须进入统一计划与用户决策流程 |
| [预览与选项弹窗][modals] | Obsidian 原生 Modal、分组路径列表、确认/取消、已有勾选控件 | 普通同步预览目前只是整份清单确认，需增加逐项选择；旧副本清理不是冲突内容决策 |
| [本地文件适配][local-vault] | 二进制读取、内容编码、文件操作、状态计算 | 隐藏路径过滤不能叫作 Git 跟踪状态；读取失败不能解释成文件不存在；写入失败需返回已成功项目 |
| [GitHub 适配][remote-vault] | Octokit、远端树和内容读取、blob/tree/commit/ref 操作、错误包装 | 发布必须绑定已审阅的分支状态；修正请求实际启动时机及结果不明时的重复提交风险 |
| [忽略匹配][gitignore] | 已有 `ignore` 依赖及规则文件读取基础 | 多层规则、重新纳入例外、已跟踪例外、规则来源和不可读取状态不能只靠当前布尔过滤完成 |
| [插件入口][main]和[设置页][settings] | 已有中文界面、GitHub 认证、仓库/分支、通知、命令和图标 | 默认双向入口改为先预览；移除周期注册和旧自动执行，新增打开知识库仅检查开关 |

两个已核验、应列入早期测试的具体问题：

1. [单向计划生成][directional-policy]按来源相对缓存的变化决定写入：来源没变但目标缺失时会漏补；来源被记为新增但目标已存在时，旧“只增”分支也会写入。不能仅重命名按钮就算满足新需求。
2. [远端上传队列][remote-queue]在构造数组时已创建请求 Promise，后续按间隔逐个等待不能限制这些请求的实际发起速度。应改成惰性任务，不照抄注释里的速率声明当作已实现。

## 3. 最小结构调整

### 3.1 沿用现有结构，不引入新框架

```text
现有命令 / 图标 / 设置页 / 打开知识库检查
                    ↓
       读取快照 + Git 规则上下文
                    ↓
       共用计划生成器（六类规则）
                    ↓
    现有弹窗增强：选择、差异、决策
                    ↓
       共用执行器 + 发布前置条件
                    ↓
       逐项结果 + 最小同步状态
```

优先在[现有单向核心][directional]中扩展统一计划和执行骨架；将原双向入口转接至该流程。只有纯规则函数难以测试或文件明显失去边界时，才拆出一个轻量的 `syncPolicies.ts`。不为每种模式新建引擎、调度器或服务层。

保留[文件内容编码][content-encoding]、[本地读写][local-vault]和[GitHub 读写][remote-vault]的职责。界面只提交模式、方向、勾选集合和决策结果，不在弹窗里再计算一套同步规则。

### 3.2 最小数据模型

计划只保存完成本次操作所需的元数据，附件内容按需读取，不全量塞入弹窗或持久化计划：

- 仓库、分支及方向；规则种类。
- 准备时的远端提交、规则指纹和相关本地内容状态。
- 稳定的操作编号、路径、目标端、写入/删除/冲突种类、前置条件及依赖组。
- 当前选中项目、冲突的用户决策、必要的手工文本草稿。

同步状态分清两种用途：

- **扫描缓存**：上次看到的本地/远端状态，用于减少重复工作。
- **共同状态**：该路径上一次已经确认一致的内容，或已确认双方删除；另有明确的“未知”状态。

不能把“刚扫描过”当作“已经同步”。空目录/空仓库的合法状态也不能用“没有缓存”代替。

本地现有哈希与 Git blob 哈希不是同一种算法，禁止直接比较或相互拷贝。保留旧扫描缓存的算法标识；内容一致性使用明确的同口径摘要或字节比较，仅为需要比较的文件读取内容。旧记录不能证明双方一致时，保守转为未知，不清空认证或悄悄全量上传。

新增状态只记录摘要、必要提交标识和项目结果，不保存文件历史副本。仅演进本插件内部状态格式，不导入原 FIT 配置。

## 4. 实施阶段与交付门槛

以下人日为单人实施的初步工作量估计，不是已验证工时或日历承诺。合计约 **8—14 人日**；按阶段门槛推进，不能用后续界面工作掩盖前置语义未解决。真实设备或专用测试仓库不可用时，记录尚未验收的项目，不虚报通过。

| 阶段 | 主要工作 | 交付门槛 | 粗估 |
|---|---|---|---|
| P0：基线与可行性 | 复现现有测试/构建；确认忽略上下文、跟踪身份和并发发布方案 | 实际基线记录；关键能力验证；无功能缩水或重型依赖偷渡 | 0.5—1 人日 |
| P1：状态与范围 | 共同状态、首次未知、忽略上下文、逐项状态持久化 | 不误判删除、不吞未选变化、范围语义测试通过 | 1—2 人日 |
| P2：六类纯计划 | 用表驱动规则生成共用计划 | 模式×方向×文件状态矩阵通过，生成计划零副作用 | 1—2 人日 |
| P3：共用执行 | 绑定计划版本、发布校验、本地前置条件、部分结果、真实限流 | 并发与故障注入通过，无盲重试和虚报成功 | 1.5—2.5 人日 |
| P4：审阅与决策 | 增强现有弹窗及默认入口 | 逐项、依赖、取消、冲突决策、中文输入和二进制选择通过 | 1—2 人日 |
| P5：设置与启动 | Git 规则编辑、打开仅检查开关、移除定时入口 | 无周期调度，旧自动配置不激活自动行为，配置保留 | 0.5—1 人日 |
| P6：集成与交付 | 修正旧测试、整库场景、桌面/移动验收、体积与文档 | 必测项通过，交付物可复现，未验项明确列出 | 2—3.5 人日 |

依赖顺序：P0 → P1 → P2 → P3 → P4 → P5 → P6。P4 的原生控件草图、P5 的定时配置清理可与 P2/P3 的不同文件任务并行，但不得各自复制规则或并发改同一入口。负责整合者统一串行处理入口、类型和状态格式。

### P0：先证实能力，不先做大界面

1. 开工前记录当前工作树、已有产物与运行环境；不克隆新副本，不安装到真实知识库。
2. 在现有依赖基础上运行类型检查、现有单元测试及生产构建，真实记录数量、失败和耗时。构建会覆盖源码工程的 bundle，必须作为后续已授权开发操作执行，不能在本次计划阶段运行。
3. 核验两项技术门槛：
   - **Git 原生语义来源**：FE 使用 GitHub API，插件缓存不等于 Git index，GitHub 树也不能提供设备的本机/全局配置。逐平台明确能读取的规则源、Git 跟踪身份及缺失/拒绝读取状态。
   - **远端并发发布**：固定预览分支头并验证原子条件发布候选；不能把一次执行前检查或普通 REST 更新称作严格比较交换。
4. 使用隔离 fixture 做最小验证，禁止靠读取真实用户令牌、真实 Git 配置或真实笔记补洞。
5. 若现有平台 API 无法满足某项已定语义，先输出具体证据与最小方案，不悄悄缩水，也不为完成计划而引入完整 Git 客户端。该门槛只阻止相关功能进入“已完成”，不要求现在再泛泛重问产品需求。

### P1：范围、规则与共同状态

1. 将“Git 已跟踪”“本地文件能否读取”“参与 FE 同步”区分命名和数据来源，不继续混用 `shouldTrackState()`。
2. 保留整个知识库的原始存在信息、规则排除信息和读取失败信息，再生成有效同步集合。不能先丢掉忽略项，随后把丢失当成应删除。
3. 笔记和附件为内容范围；设置、主题、插件目录由 Git 排除配置管理。需要补充共享规则时，在已有编辑入口展示实际改动，用户保存，不另建隐藏排除清单。
4. Git 仓库内部元数据及插件运行状态不是用户笔记，不能进入镜像写删清单。历史冲突副本不得因新流程而被自动清理或当作普通笔记上传。
5. 共享规则文件本身需要被读写、比较并能随 Git 提交共享，不能继续被“所有点文件禁用”误拦。规则文件是控制元数据，不表示扩大为同步 Obsidian 设置目录。
6. 复用 `ignore` 依赖实现规则优先级、有效重新纳入例外、逐文件来源说明；用 Git 在隔离仓库中的实际结果作测试参照。
7. 本机排除和个人全局源只读；可用、未配置、不可访问必须分别表达。不能用运行开发代理的 WSL 全局规则冒充移动设备或用户桌面的规则。
8. 对已跟踪的 Obsidian 设置目录显示需要 Git 处理的提示，不悄悄取消跟踪、不用新增忽略规则假装处理完成。
9. 初次扫描：双方同名且内容一致可在确认后建立共同状态；内容不同不得采纳为共同状态，但处理结果由模式决定：补缺跳过目标已有文件，覆盖/镜像按来源列入预览，单向更新及两种双向规则在缺少依据时交用户决策。旧“零上传采纳两边各自状态”不能被当成双方已经一致。
10. 未选、冲突未决、失败、结果待确认的项目不推进共同状态；仓库/分支身份变化不能复用另一仓库的共同状态。

**P1 特别门槛**：移动端无 Node/系统 Git。若精确取得本机 index 或个人规则在平台上不可实现，须在 P0/P1 给出具体能力差异并取得必要的方案调整批准；不得只复制 GitHub 树或 FE 缓存，然后对外宣称完整实现 Git 原生索引语义。

### P2：六类规则，先用测试定义结果

将模式和方向作为规则输入，扫描快照与共同状态作为数据输入，纯函数输出操作计划。无网络、无文件写入、无持久化。

- 补缺、覆盖和镜像按当前双方内容/存在性决定，不以来源上次是否变化为唯一条件。
- 单向更新及两种双向规则按共同状态区分单方改动、双方改动；首次未知不猜测历史。
- 双方结果相同不报冲突。对内容不同：补缺跳过目标已有文件；覆盖/镜像以来源列入预览，不另加冲突裁决；单向更新及两种双向规则只对按其规则确需裁决的分歧交用户决策，不按修改时间自动选胜方。路径碰撞等无法直接执行的问题另行作为执行冲突处理。
- 双向不传播删除不做智能改名清理：新旧路径按已定规则保留或补回。
- 写入与删除同一路径、文件与目录碰撞、不同路径映射到同一实际文件等情况形成显式冲突或依赖组，不能独立乱序执行。
- 路径规范化不擅自改名；拦截越出知识库边界的路径，测试中文、Unicode 规范化、大小写冲突。
- 旧“只增＋删独有”不能冒称镜像，也不自动增加为本轮第七种算法；旧入口转为已确认模式选择，不重命名掩盖行为差异。

### P3：执行正确性与故障处理

1. **唯一执行入口**：手动、命令、设置按钮及启动检查产生的计划共用执行器；只使用短期运行互斥，不建立用户可见的暂停状态机。
2. **确认前零应用**：检查和内容获取不写用户文件、不发布远端提交；取消不推进共同状态。
3. **执行前复核**：仓库/分支身份、远端头、本地相关路径状态、规则指纹都绑定到计划。失效则返回重新检查，不自动改变用户选项后继续执行。
4. **本地操作**：相关内容按需准备；逐路径执行前检查目标存在性/类型及内容前置条件。必须处理执行期间文件再次变化，不将插件互斥误认为能锁住用户或其他插件的编辑。
5. **远端发布**：本次已选远端动作尽量形成一个提交，保留未选路径和排除对象。现有 REST 适配不能在执行时换用新分支头并套用旧计划。
6. **严格头条件候选**：GitHub 官方 `createCommitOnBranch` 提供 `expectedHeadOid`，可作为现有 Octokit 的轻量候选，而不是新增 Git 客户端。先验证载荷、附件、权限、空仓库/空分支及现有加密编码兼容；它不能假定直接引用已有 REST blob/tree 上传结果。参考[GitHub 官方提交接口文档][github-conditional-commit]。
7. **不静默降级**：候选不适用时，不能退回无条件更新却继续宣称有严格并发保证。固定父提交＋非强制更新只能覆盖特定竞态，不能当作通用 CAS；替代路径必须在 P0/P3 证实其具体保证。
8. **空仓库**：单独设计首次建分支流程，校验创建竞争；不得因无 HEAD 就退化成强制推送。
9. **限流**：把“已启动 Promise 列表”改成惰性请求队列；约束真实开始时间和在途数量，按实际响应区分限流与权限错误。不把旧注释中的固定速率作为服务端永久保证。
10. **部分失败**：本地适配返回逐路径成功、失败；远端返回发布提交及明确成功/失败/待确认。双向操作不承诺跨本地和 GitHub 的原子回滚。
11. **响应丢失**：先查询实际远端头及提交结果；未确认前不盲重试写入，不把 `clientMutationId` 当成服务端幂等保证。
12. **状态保存失败**：明确提示已发生的文件/远端结果；下次先扫描核对，不用旧状态再次覆盖。只保留操作编号、提交标识和未决项目等最小元数据，不存历史内容。
13. **依赖与基线**：按依赖组确认完成；某一端成功而另一端失败，不得标成已经双向一致。失败后的继续复用正常检查与审阅，不新增恢复中心。

### P4：增强现有审阅界面，不做重型客户端

1. 沿用现有图标、命令和原生弹窗；默认入口固定生成双向传播删除计划。单向入口统一选择四类规则和方向，双向入口选择两类规则，不增加大量独立工具栏按钮。
2. 预览显示方向、模式、受影响路径、新增/修改/删除/冲突计数；增加逐项选择、全选、取消及依赖组联动。未决冲突不能被默认“全选”裁成某一版本。
3. 冲突在同一审阅流程中呈现本地、远端与选择结果；文本按需加载，使用原生控件或现有 Obsidian 能力进行轻量比较和草稿编辑。确认前草稿留在内存，不覆盖正文。
4. 二进制展示文件类型、大小及版本选择，不将其当 UTF-8 文本编辑。必要时使用已有打开方式查看附件，不开发附件编辑器。
5. 长清单分组、折叠或按需渲染；不同时把所有附件内容加载到 DOM。
6. 取消、关闭弹窗返回既有流程，无后台悄悄继续；无“暂停/恢复”按钮、锁定模式或额外重复确认。
7. 已有冲突副本清理仅作为历史兼容功能隔离保留，不自动生成副本替代新决策，也不自动删除历史副本。默认同步流程不依赖清理功能。

### P5：设置与打开知识库检查

- 保留现有认证、仓库/分支、设备、必要通知设置，不新增账户管理器。
- 新开关建议字段为 `checkOnVaultOpen`，默认 `false`。

- 旧 `autoSync`、间隔字段不映射为新开关开启；移除 onload、保存设置、卸载中的旧周期任务注册/管理和定时执行分支。
- 移除定时间隔和旧自动执行选项。旧字段可以为兼容暂存但不再消费，不能清空其他 FE 配置。
- `.gitignore` 编辑复用原生多行输入，显示即将修改的共享规则；保存使旧计划失效。本机/全局来源仅只读展示，不复制成 FE 第二套规则。

## 5. 必测矩阵

### 5.1 文件状态用例

| 用例 | 核验重点 |
|---|---|
| 来源有、目标没有，来源相对历史未变化 | 补缺和覆盖/镜像不能漏补；单向更新须区分目标主动删除 |
| 来源“新增”、目标已存在且不同 | 补缺绝不能覆盖 |
| 目标单独改动 | 单向更新保留；覆盖/镜像以来源为准 |
| 双方修改且相同 / 不同 | 相同不报冲突；不同按模式断言：补缺跳过，覆盖/镜像以来源列入预览，单向更新及两种双向规则对确需裁决的分歧返回用户决策 |
| 一端删除、另一端未改 / 也修改 | 传播删除与不传播删除行为不同；删改冲突不自动选胜方 |
| 双方都删除 | 明确共同删除状态；不从历史凭空恢复 |
| 无共同状态，同名相同 / 不同 | 相同可确认建立共同状态；不同不冒充共同状态：补缺跳过已有文件，覆盖/镜像按来源列入预览，单向更新及两种双向规则交用户决策 |
| 空仓库、空知识库、空文件、仅一侧有内容 | 未知、空与删除不能混为一谈 |
| 改名、大小写或 Unicode 等价路径 | 不传播删除模式保留旧路径；实际路径碰撞需决策 |
| 目标独有的未跟踪 / 被忽略文件 | 镜像可删前者，不得把后者当成来源删除 |
| 已跟踪后新增忽略规则 | 不假装自动停止跟踪 |
| 原生共享规则、本机规则、不可访问源 | 优先级、有效反选、来源及能力状态准确 |
| 图片、PDF、中文、无效 UTF-8、较大附件 | 字节往返一致，严格解码，不乱码或误编辑 |

四类单向规则各测上传/拉取；两类双向规则测交换本地/远端后的对称结果。所有模式复用相同审阅行为，不出现“某个旧入口绕过确认”的例外。

### 5.2 审阅与故障注入

- 取消、全不选、只选一部分、依赖组部分选择、未决冲突全选。
- 预览后本地新增/修改/删除，远端推进或重置，规则变动，仓库或分支切换。
- 远端头在执行前检查之后变化；发布前置条件不满足。
- 上传成功但响应丢失，远端成功但本地失败，本地部分失败，持久化失败。
- 设备前后台切换、断网、权限不足、限流、重复点击、卸载时尚有异步检查。
- 重开插件后仍识别未选/未完成项目，不把真实未完成操作消失在基线里。
- 空分支同时被另一个客户端创建；不强制覆盖。

## 6. 轻量化验收

轻量化不是忽略正确性，而是避免为每条边界创建独立子系统。

1. **依赖**：新增运行时依赖目标为 0；优先保留现有 Octokit、retry、ignore。不引入完整 Git 实现、Monaco、重型差异编辑器或状态管理框架；如确需新增，单独说明必要性及 bundle 增量，不能静默加入。
2. **结构**：共用计划与执行；只在确有测试/职责边界收益时拆文件，不搭通用同步平台。
3. **后台成本**：没有定时轮询；启动开关关闭时不发起同步检查；开启时只做一次必要检查，不构建后台索引服务。
4. **内存与 I/O**：扫描和内容读取有界并发；元数据按文件数增长，附件按需读取并释放；不能声称所有扫描都是零内容读取，也不以时间戳直接决定版本胜负。
5. **网络**：使用远端提交/树缓存、按需获取内容；只为实际需要的远端写入生成内容请求；不得为了本地审阅上传整库。
6. **产物**：以同一生产构建配置比较当前 310,041 字节主 bundle 的增量，列出归因。工程预警线建议设为增幅 15%；超过时先复核重复代码及依赖，不为追数字删已确认功能。该预警线是计划建议，不冒充用户已指定的硬上限。
7. **性能记录**：P0 记录空变更检查、少量修改、较多路径和大附件场景的时间、内存及请求数；P6 同场景复测。不在缺少实测时编写毫秒级承诺。
8. **兼容**：保留当前最低 Obsidian 版本配置；不擅自宣称更老版本已验收。不在插件运行时代码使用 Node 内置模块、`Buffer`、`process`、`require`；二进制读取与严格解码复用现有兼容实现。
