# Fit-Extended（FE）需求说明（本轮已确认）

状态：用户已整体确认本轮需求，并要求复核是否存在其他必要澄清项。复核结论：没有阻止本轮产品范围定稿的未决选择；剩余事项归入实现设计与验收约束，不扩展功能范围。本次确认不授权开发、安装或实际同步，也不代表现有插件已实现下列功能。

## 1. 总体边界

- **轻量化是硬约束**：定位为同步工具，不扩展为完整 Git 客户端。
- 七项能力尽量共用同一套操作计划、预览、冲突处理和执行流程，通过规则差异实现，不各建一套功能系统。
- 优先复用现有 FE 代码与依赖，不为同步功能引入完整 Git 客户端、重型编辑器或管理框架；只保留判断变化和继续操作所必需的状态。
- 不增加文件管理器、日志中心、备份管理器或常驻定时任务。必要的操作结果、错误及规则来源在现有交互中简洁展示，不另建管理模块。
- 用户内容同步范围为笔记和附件；不需要同步 Obsidian 的设置、主题和插件文件。通过 Git 排除配置实现，不另建 FE 排除清单；已有跟踪状态不得擅自变更。
- 远端服务仅支持 GitHub；本次不扩展 GitLab、Gitee 或通用 Git 远端。
- 以工作区内已经编写的 FE 版本为开发基线，在现有实现上增改，不从零重写，不另建一套插件工程；本阶段只明确需求，不继续核对 GitHub 或开展实现。
- FE 相对原 FIT 使用独立插件身份和配置；这不表示需要重新创建插件，也不表示重置已有 FE 配置。不做原 FIT 配置导入或迁移。
- 七项同步能力全部纳入；缺少现成 Git 模式的部分可由 FE 补充实现。这不等于要求暴露全部 Git 命令及参数。
- 后续设计首先复用已有代码和技术路径；只有为满足确认需求确有必要时才讨论局部调整，不默认重选技术栈。

## 2. 七项同步能力

操作入口的作用范围固定为整个知识库，不提供指定目录或单个文件的独立同步入口。预览计划中已议定的逐项选择、全选与取消保持不变。

以下“来源”和“目标”表示操作方向，不固定对应本地或远端。文件处理均限于知识库内实际参与同步的内容；忽略规则见第 5 节。

| 编号 | 能力 | 已确定的行为 |
|---|---|---|
| 1 | 仅补充缺失文件 | 来源有、目标当前没有则补充；包含目标曾主动删除的文件。同名文件不覆盖，目标独有文件保留。 |
| 2 | 单向更新 | 按上次共同状态比较内容。仅来源修改则更新目标；仅目标修改则保留；双方结果相同则无需操作；双方修改且内容不同则报冲突。无共同状态且同名内容不同时不自动覆盖。补充来源新增文件，不传播来源的文件删除，保留目标独有文件。目标主动删除而来源未修改则保持删除；来源也修改则报冲突。 |
| 3 | 单向覆盖 | 来源存在的文件以来源内容为准，缺失则补充；保留目标独有文件，不将其删除。 |
| 4 | 单向镜像 | 在整个知识库实际参与同步的范围内使目标与来源一致，包括删除目标独有文件。删除范围不局限于 Git 已跟踪文件，也可包含未跟踪文件；被忽略而排除的文件跳过，不因来源清单没有它们而删除。 |
| 5 | 双向合并、不传播删除 | 交换新增和修改；一端缺失、另一端仍有则补回，允许文件复活。双方都没有的文件不从历史自动恢复。重命名不作为删除规则的例外：新增新路径，旧路径仍保留或补回。 |
| 6 | 双向同步、传播删除 | 根据历史识别并交换新增、修改和删除。删除与修改等未决冲突展示差异并返回用户决策，不自动判任一方获胜。 |
| 7 | 人工审阅后同步 | 可与前六项组合，而非第七种互斥差异算法。展示操作计划，支持逐项选择、全选、全部取消；依赖操作需联动选择。未选操作不得视为本次已同步。 |

“不传播删除”指文件级删除，不表示禁止同步文件内部文字的删改。

## 3. 默认操作与冲突

- “一键同步”默认采用：双向同步、传播删除，先审阅再执行。
- 确认前不应用计划中的文件变化、不发布同步结果；检查远端状态与获取比较所需数据不等于执行同步。
- 需要裁决的冲突直接返回用户决策：展示双方差异，用户可选择本地、远端或手工编辑结果，再按既有审阅流程确认执行。不另设暂停按钮、锁定状态、恢复流程或额外确认步骤；不将此前“暂停”的措辞扩展成新的全局停止规则。
- 单向覆盖、镜像中已经明确按来源取值的普通内容差异，不应被当作需要重新裁决的冲突。
- 不因增加“补回”规则而把其他模式误称为镜像；镜像还包含目标独有文件删除及来源内容优先等规则。

## 4. 触发方式

- 默认手动触发同步检查和计划生成。
- 设置“打开仓库时自动检查变化”的独立开关，默认关闭。
- 开启后，在打开仓库时自动检查，发现差异生成待审计划，不自动执行同步。
- 关闭此开关不影响手动同步。
- 不设置此前误解产生的“是否启用整个仓库同步”的总开关。
- 不做定时同步功能。其他后台触发行为未经确认，不得擅自增加。

## 5. Git 忽略规则：单一规则来源

- 不维护独立的 FE 排除清单；FE 直接提供 Git 忽略规则编辑入口。
- 仅允许编辑当前仓库共享的 `.gitignore` 规则文件。
- 当前仓库的本机排除、个人全局忽略规则参与 Git 原生匹配，但在 FE 中只展示、不修改。
- 展示文件是否被忽略及对应规则来源。
- 遵守 Git 原生语义：匹配忽略规则的未跟踪文件不纳入同步；已跟踪文件不因新增忽略规则而自动停止跟踪。
- 不擅自取消文件跟踪，不额外制定 FE 专有排除优先级。
- 被忽略而排除的文件属于跳过对象，不属于镜像时应删除的目标独有文件。

## 6. 轻量化与历史恢复

- 版本历史查看、恢复和回退交给插件外的 Git 工具。
- 撤销本会话中途提出并曾选择的“内置文件历史、版本恢复、整次同步回退”方案，不纳入本次范围。
- 不维护额外备份库，不制作回退界面。
- Git 历史不能直接恢复从未进入历史的文件内容；不得对未记录状态承诺恢复能力。

## 7. 已否定或被替代的方案

- 独立 FE 排除规则：已取消，改用 Git 原生忽略规则。
- 定时同步：不做。
- 仓库同步总开关：源于误解，不是用户要求；正确需求是打开仓库自动检查的开关。
- 内置历史查看、恢复和整次回退：已撤销。
- 冲突时默认自动选一方或保存冲突副本后继续：不是选定的默认行为。
- 因新问题而改变此前单向更新的删除处理规则：用户明确不需要改动。

## 8. 定稿复核：实现设计与验收约束

以下是落实已定需求时的正确性约束，不是新增功能，也不要求现在再逐项选择。应优先用现有流程中的少量状态校验和提示实现，不能逐条扩建成独立管理模块。具体实现方案须待开发或设计授权后制定。

- 入口与兼容：在既有 FE 界面和代码基础上组织各单向能力、明确操作方向，保持已有桌面与移动端兼容，不另建 Git 管理器。
- 已跟踪的非同步内容：若 Obsidian 设置、主题或插件文件已经被 Git 跟踪，新增忽略规则不会将其排除。应明确提示这一状态，不能悄悄继续同步这些内容，也不能擅自取消跟踪；仓库状态调整由用户通过 Git 处理。
- 首次及部分同步：无共同状态时不得把无法判定的差异当成已知删除；部分执行后，只更新实际成功项目的同步状态，未选及失败项目不得标成已同步。
- 计划过期：审阅期间本地或远端变化，或用户修改了影响计划的忽略规则，执行前必须重新核验；不能继续按已经失效的计划覆盖或删除。
- 忽略差异：明确规则变更的生效顺序，能说明不同设备本机规则导致的范围差异；不另设 FE 排除清单。
- 路径与二进制冲突：文件与目录同路径等无法直接执行的情况按冲突处理；二进制文件不得冒充文本合并。双向不传播删除模式的重命名仍严格遵守保留旧路径的已定规则。
- 中断及失败：如实区分已完成、未完成与结果待确认，不虚报成功；再次操作前核对实际状态，不盲目重复提交。此约束不增加自动回退或额外备份库。
- 镜像：验证未跟踪文件的删除范围；不触碰排除对象或同步范围外文件。

## 9. 需求验收框架

仅在后续获得开发授权后，以隔离测试目录验证：

1. 七项能力分别覆盖新增、同名差异、目标独有文件和删除场景。
2. 同步入口只作用于整个知识库，不增加目录或单文件入口；默认先审阅，逐项选择及冲突返回用户决策符合约定，不增加独立暂停或恢复功能。
3. 打开仓库自动检查开关默认关闭，且无定时同步。
4. Git 忽略规则单一来源，已跟踪与未跟踪文件语义正确，镜像不误删排除对象。
5. 不出现已撤销的 FE 排除清单、内置历史恢复或仓库同步总开关。
6. 覆盖首次无共同状态、部分选择、计划过期与中断场景，不能误判删除、误报成功或重复执行结果不明的操作。
7. 验证设置目录已跟踪、路径碰撞、二进制冲突及现有桌面与移动端兼容，不因轻量化破坏核心行为。
